ICM occupancy · SIGReg · scalar distance code

Why the code folds

An encoder learns a one-number code for distance from a wall. Under SIGReg, the code sometimes turns back on itself, so two different distances get the same code. This page explains when and why, using nearly 500 trained encoders.

The short answer

A fold needs three things at once. Remove any one and it goes away. The first two are established by controlled tests. For the third, we know it matters causally but not yet exactly how it works.

The force

A target shape for the codes

SIGReg wants the histogram of codes across visited states to look like a bell curve. InfoNCE has no such target, so it never folds.

The material

A lopsided histogram

The exploring agent spends most of its time near the wall. Those states pile into a spike of codes, and the rest form a tail. The target shape then pushes to reposition and rescale the spike and the tail.

The response

An encoder that bends under that pressure

From an identical start, changing only what the encoder can move changed whether it folded. Exactly how the encoder turns the pressure into a bend is still open.

What a fold looks like

Each line is a trained code as a function of distance. A good code rises steadily. A folded one rises, then turns back down over codes it already used.

1. The force: a target shape for the histogram

The code is a function of distance, so its histogram is just the agent's occupancy pushed through that function. Objectives differ in whether they care what that histogram looks like.

InfoNCE compares codes through a learned critic, and the critic can absorb any monotone relabelling of the codes, so a lopsided histogram costs it nothing. Adding a skewness penalty, and nothing else, makes InfoNCE fold on the same data. That was a pre-registered test.

2. The material: where the force pulls

For a one-number code, SIGReg's pull on each code can be written exactly: blur the code histogram with a unit Gaussian, subtract a blurred bell curve, and every code slides downhill on the difference. The spike is a hill, so its codes are pushed outward. The gap after it is a valley, so tail codes between the valley and the tail's own crest (shaded) are pulled back toward the spike. Codes past the crest slide outward.

Balanced (m ≈ 0.5)

Spike and tail weigh about the same. The tail sits in the valley and just compresses.

Lopsided, tail in reach (m ≈ 0.6–0.9)

The whole tail lies in the pull-back band and gets dragged toward the spike.

Tail out of reach (m ≳ 0.92)

Much of the light tail starts past its crest and slides away. SIGReg fits the spike alone by inflating the code scale.

3. The response: the encoder turns the pressure into a bend

In a folding run, the tail's far end drops past the tail's middle, and the code curve turns back. The baseline encoder sees tanh(4x) with x ∝ 1/distance, which spreads the far region across most of its input. An unsquashed input, x, crowds the far tail together; there the tail moves as a block and never folds. We tested two explanations for why the bend happens, and both failed (below).

The test that changed the story

We first thought the fold won a race against stretching the spike. To test that cleanly, we gave the baseline encoder one extra input channel whose weights start at zero. The starting code, and so the starting histogram, stays bit-for-bit identical, but the encoder gains a new way to move certain states.

Extra channelm = 0.625m = 0.75m = 0.875
near-wall only (spike can stretch)fold 4/4fold 4/4no fold 4/4

At m = 0.75 the spike stretched twice as fast with the near-wall channel, yet the tail's far end crossed its middle at step 300, the same step as the control. Stretching the spike does not stop the fold there. At m = 0.875 the same starting histogram stopped folding, so what the encoder can move does change the outcome causally.

Which part of SIGReg's pull is needed?

We kept the loss value the same and changed only how SIGReg's gradient reaches the codes. With the spike and the tail each allowed only to move as a block and change their spread, four numbers per batch, the fold still formed every time, at the same size. Moving the blocks alone, or changing spreads alone, did not fold.

What SIGReg can do to the codesFolds?

Both as blocks: position onlyno, 0/8 (stays skewed)
Both as blocks: spread onlyno, 0/8 (scale blows up)

So the pressure that causes the fold is coarse: the spike and the tail must be repositioned and rescaled together. The fine shape of SIGReg's force does not matter.

Putting it together: the phase map

Varying the near mass and the input squashing together gives three end states. Folds fill a wedge at strong squashing. A fold is easiest near m ≈ 0.7, where the histogram is lopsided enough to pull hard and the tail is still within reach.

Still open

The next step is to find how the encoder converts block-level pressure into a bend: which parameters carry it, and where along the tail it starts. Then freeze those parameters from an identical start and see if the fold disappears. After that, a reduced model that reproduces the shape of the fold wedge from the spike's stretch speed, the tail's bend speed and the landscape's band. Whether the inflated state eventually escapes. Whether wider or deeper encoders, or encoders that compress the near region in other ways, give the same map.
